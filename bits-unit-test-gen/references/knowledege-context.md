# 说明

按照以下步骤，获取本次单元测试涉及到的用户意图、研发活动背景、仓库属性知识和规范等上下文。

# Step1 准备

识别项目的编程语言（赋值给变量 `LANG`，取值为 go/python/java/javascript/kotlin/cpp/swift 之一）。识别结果无需在对话中输出。

若无法判断语言或语言不支持 → 终止并告知。

# Step2 加载全局上下文
- 如果用户有给定`${FEATURE_DIR}`变量，则设置 `${EXEC_SOURCE}` 为 `flux`
- 如果用户有给定`${FEATURE_DIR}`变量，且该目录下存在 `spec.md` 文件，则读取该文件，来获取更多的用户意图上下文信息。
- 在根目录 `${PROJECT_ROOT}` 下，如果存在 `AGENTS.md`、`CLAUDE.md`，则读取其中与单元测试相关的部分（命名约定、测试框架偏好、目录结构规则等）。


# Step3 加载语言知识

读取 `${SKILL_ROOT}/assets/${LANG}/prompt.md`，获取语言特定的单测知识，包含：

- 最小执行单元定义
- 最小生成/验证粒度
- 目标函数提取方法
- 补充文件过滤规则
- 测试文件命名与组织约定
- Mock/断言框架选择
- 编译与执行命令
- 预检查要求



# Step4 确定单测生成范围
支持以下模式：

1. **已指定范围**：用户明确指定了生成范围（如函数、对象、文件、包、或传了变量 `${TEST_SCOPE}`），直接按该范围生成。
2. **测试函数入手**：用户选中或提及了一个已有的测试函数/测试文件，需反向定位其对应的被测业务函数，以该业务函数作为生成/修复/保鲜的目标范围。
3. **基于 diff 范围**：用户提及基于工作区变更（代码 diff）来生成单测，通过 `git diff` 指令来获取改动的业务函数或文件的范围。
4. **未指定**：用户没有规定任何范围或意图，则引导用户选择上述模式之一，或自定义一个筛选规则。

# Step5 开发背景理解
结合上述生成范围，分析本次代码研发活动的用户意图：

1. 通过 `git diff` 获取工作区未提交的生成范围内的代码变更进行分析
2. 确定研发活动类型：`feature`（功能开发）/ `bug-fix`（缺陷修复）/ `refactor`（重构）/ `test`（补充测试）/ `other`（其他）


# Step6 学习已有测试风格
生成或修改测试前，阅读目标函数/文件对应的已有测试文件，学习：
- Mock 策略
- 断言风格
- 命名约定
- Import 模式

以此作为生成测试的风格模板。若无测试参考，可考虑在更大范围内学习已有测试代码。

# 规则优先级

当发现某知识在不同来源中存在冲突时（如规范要求等），按以下优先级摄取（从高到低）：

1. 用户显式指令
2. 项目单测约定（`AGENTS.md` / `CLAUDE.md`）
3. 仓库中已有的测试风格
4. 语言特定规则（`assets/<lang>/prompt.md`）
