# 单元测试缺陷挖掘

本文用于指导模型在单测生成前，从目标代码或变更代码中挖掘可供后续单测验证的真实缺陷。核心产物是 `BUG_MAP`：它是后续缺陷探测单测的唯一来源。

核心策略：**先放宽召回，尽量多提出疑点；再用严格过滤和降噪规则压掉误报。** 最终只输出降噪后的 `BUG_MAP`。

## 1. 工作流

1. **确定范围**：只使用 `scope.md` 输出的 `scope_type`、`TARGETS`、`diff_context` 和 `fallback_notes`。不得要求上游提供完整 `diff_content`。
2. **广召回候选**：从 `TARGETS` 中的目标单元、diff hunk、同 diff 直接调用方/被调用方、代码注释、日志或错误处理中承认的异常行为中召回疑似缺陷。
3. **逐个闭环**：每个候选都要补齐触发路径、根因、错误结果、正确期望、归因范围和后续可验证条件。
4. **严格过滤**：按范围、证据、噪音逐层淘汰。
5. **输出 `BUG_MAP`**：只输出通过全部门禁的缺陷；没有缺陷时输出空数组。

## 2. 候选召回范围

1. 缺陷挖掘的唯一代码事实来源是本地当前 checkout 后的工作区源码，包括当前文件内容、staged/unstaged/untracked 变更对应的实际文件内容。
2. 候选来源应围绕当前代码尽量覆盖，宁可先召回再过滤：

有 diff 时：

- `bug_range` 必须与本次 diff hunk 相交，或位于本次 `untracked` 文件目标单元内，或根因必须来自同 diff 中的契约变化。
- 优先审查 `+` 行和它直接影响的上下文。
- 只要 `diff_context` 非空，就必须使用变更信息挖掘缺陷；即使用户仅指定文件、目录、包或模块，`TARGETS` 也已是显式范围与本地变更的交集。
- 必须基于 `diff_context.files[].mode`、`diff_context.files[].range` 和 `diff_context.files[].file_path` 获取真实变更：`cached` 使用 `git diff --cached -- <file_path>`，`unstaged` 使用 `git diff -- <file_path>`，`merge_base` / `endpoint` 使用对应 `range`，`untracked` 直接读取文件内容。
- `diff_context.files[].hunks` 只作为定位索引，不替代真实 hunk 或未跟踪文件内容；进入门禁前必须按文件读取局部变更。
- 每个进入门禁的候选都必须实际读取相关 hunk 或未跟踪文件内容，并在 `BUG_MAP.evidence` 中写清候选与变更的归因关系。
- 不得把未变更代码中的存量问题写入 `BUG_MAP`，除非本次 diff 改变了触发条件或调用契约。

> 不同语言特定缺陷挖掘模式，请查阅对应 `assets/${LANG}/prompt.md`中对应部分，补充语言相关信息
> - JS/TS：额外加载 `assets/javascript/references/defect-scoring.md`（严重性评分）和 `assets/javascript/references/defect-verifier.md`（3-Gate 置信度验证）
>
> **冲突解决规则**：当本文件的通用规则与 `assets/${LANG}/` 下的语言特定规则存在冲突时（如数量限制、严重性分级标准等），以语言特定规则为准。

无 diff 时：

- 当 `scope_type=non_diff` 或 `diff_context=null` 时，只扫描 `TARGETS` 中的目标单元及其直接可验证调用链。
- `TARGETS[].source` 只说明范围来源，例如 `explicit`、`test_entry`、`untracked`；不得把来源字段当作额外扩大范围的理由。
- 可以报告存量真实缺陷，但必须与 `TARGETS` 中目标单元的实现或契约直接相关。
- 不得因为无 diff 自动输出空 `BUG_MAP`；无 diff 只限制搜索范围。


## 3. 缺陷准入门禁

候选进入 `BUG_MAP` 前必须同时满足：

| 门禁 | 要求 |
| --- | --- |
| 定位 | `bug_range` 指向最小连续代码范围 |
| 归因 | 有 diff 时与 hunk 或同 diff 契约变化相关；无 diff 时位于目标函数直接范围 |
| 触发路径 | 能说明正常业务输入或 mock 依赖如何执行到该代码 |
| 根因 | 能指出错误值、错误分支、错误状态或错误副作用如何产生 |
| 错误结果 | 会导致返回值错误、状态错误、功能失败、panic、卡死、数据损坏或业务成功/失败错配 |
| 正确期望 | 写明正确结果、当前错误结果和后续可验证条件 |
| 降噪 | 未命中第 4 节误报过滤规则，或能用代码证据反驳过滤规则 |

对吞错、默认值成功返回、nil/zero 误用、部分结果继续使用等高误报候选，必须完成三段证明：

| 证明段 | 必须回答 |
| --- | --- |
| 被调用方失败语义 | 被调用方在什么正常输入或 mock 状态下返回 error、nil、zero 或部分结果 |
| 当前函数处理契约 | 被调用方返回 error、nil、zero 或部分结果时，当前函数是否承诺返回错误、非空结果、完整字段、幂等状态或可观测副作用 |
| 可观测坏结果 | 当前函数忽略或误用被调用方结果后，会在返回值、状态、副作用或上层调用处产生什么可观察的错误结果 |

任一证明段缺失时，不得进入 `BUG_MAP`；该疑点在本阶段直接过滤，不输出给后续阶段。


## 4. 高优先级降噪规则

以下类型默认过滤，除非能给出明确代码级反证：

- **缺少业务闭环**：只指出空值、边界、并发、安全、资源风险，但说不出正常触发路径、错误业务结果和正确期望。
- **不影响功能正确性**：性能、风格、命名、可读性、架构建议，无法证明造成错误返回值、状态、功能、数据、panic 或卡死。
- **仅凭语义猜测**：结论主要依赖函数名、变量名、注释、产品意图，缺少调用方/被调用方契约、接口/IDL 契约或数据流证据。
- **泛化防御建议**：机械要求补 nil、长度、类型、default 分支；除非正常业务流会传入该值且违反声明行为。
- **存量约定已覆盖**：同类写法在存量代码中稳定存在，或参数、配置、请求体已由上游校验。
- **责任不在本次变更**：根因位于未变更 helper、ORM/RPC/SDK/IDL getter、基础设施默认行为，且当前 diff 没有误用证据。
- **非关键副作用**：日志、指标、缓存预热等失败被忽略；除非调用方明确依赖该副作用做重试、路由或分支决策。
- **服务边界转换**：错误包装、错误码转换、默认值兼容属于既有边界契约，除非调用方依赖原始错误或字段。
- **框架托管契约**：框架明确保证的行为不得反向怀疑，例如 Go RPC/protobuf 在 `err == nil` 时响应非 nil，连接池资源由框架托管。
- **不可稳定触发**：只能靠竞态窗口、真实网络波动、外部服务状态、当前时间或随机数触发，无法用固定输入或可控依赖稳定构造。
- **验证缺口反向证明不足**：现有覆盖不足、缺少用例或缺少校验，不等于代码有缺陷。
- **低置信兼容差异**：新旧行为不同但没有契约说明哪一个正确，且没有调用方错误结果。

以下是补充规则：
- 不得使用 commit message、MR 标题或提交描述作为缺陷过滤依据；缺陷的召回和过滤必须完全基于代码事实和变更内容本身，commit message 仅反映作者意图，不能用于否定代码中存在的真实缺陷。

## 5. 缺陷分级和数量预算

缺陷分级只用于排序，不替代门禁：

| Severity | 使用条件 |
| --- | --- |
| P0 | diff 直接引入安全漏洞、稳定崩溃、数据丢失、核心链路整体不可用|
| P1 | 证据清晰，影响重要业务路径或关键分支，会造成明确错误结果|
| P2 | 影响范围中等或局限于边界/降级/兼容路径，但仍满足证据闭环、正确期望要求 |

数量预算：

- 每个目标函数最多输出 2 条缺陷。
- 整个任务默认最多输出 4 条缺陷。
- 超预算时优先保留：P0/P1、直接位于 diff `+` 行、后续最容易构造稳定输入、错误结果最明确、覆盖不同文件和失败模式的候选。

## 6. 输出格式

完成缺陷分析阶段时，输出：

```json
{
  "BUG_MAP": [
    {
      "scenario": "[defect-probing] 被调用方返回错误时，目标函数应返回错误而不是成功",
      "description": "忽略被调用方错误会导致成功分支返回无效结果",
      "file_path": "path/to/file.go",
      "target_func": "FunctionName",
      "bug_range": "line 45-48",
      "evidence": "Line 45 ignores err from Load; 调用方会把返回结果当作成功响应处理",
      "expect_outcome": "correct outcome: return the Load error; current wrong outcome: nil error with zero result; verification: downstream should observe a non-nil error instead of a successful zero result",
      "severity": "P1"
    }
  ]
}
```

字段约束：

- `scenario`：必须以 `[defect-probing]` 开头，描述后续可验证的缺陷场景。
- `description`：一句话说明缺陷本质。
- `file_path`、`target_func`、`bug_range`：定位到最小责任代码。
- `evidence`：合并写清触发路径、根因、错误结果和 diff/范围归因；不要拆成多个审计字段。
- `expect_outcome`：写清正确结果、当前错误结果和后续可验证条件。
- `severity`：只能是 `P0`、`P1`、`P2`。

无缺陷时输出：

```json
{
  "BUG_MAP": []
}
```

当 `BUG_MAP` 为空时，必须在缺陷分析日志或调试输出中记录候选过滤摘要，包含候选位置、疑点、读取过的证据和过滤原因；该摘要不得作为后续缺陷探测单测的输入。
