# FTF DIFF 多轮修复收敛

## Use Cases

当用户要求修复一个 FTF 回放任务的 DIFF、持续降低 DIFF 数量，或基于上一轮结果继续修复时，
使用本流程。它面向长周期、多轮执行和验证，不要求在一轮内平均分析所有聚类。

以下场景使用其他流程：

- 只需要完整的任务级归因报告：使用 `task-analysis.md`。
- 只需要分析一个 Flow 或一个字段：使用 `flow-diff-root-cause.md`。
- 只需要生成不可执行的噪音修复预览：使用 `remediation-plan.md`。

## Inputs

- 必填：可信 FTF task URL，或 task ID 加明确站点。
- 必填：本轮允许的动作范围，例如只分析、允许修改业务代码、允许预览平台配置，或已明确授权的
  具体写入。
- 可选：上一轮基线、已执行动作、验证任务、剩余聚类和受阻证据。
- 代码修复时：目标仓库、任务时点版本和当前集成基线必须来自可信代码或部署证据，不能从 DIFF
  文本猜测。

## Workflow

### 1. 建立轮次基线

先按 `SKILL.md` 冻结任务身份、站点、筛选条件和 `update_time`，再按
`task-diff-triage.md` 获取完整聚类清单。每轮至少记录：

- 有 DIFF 的接口数和流量数；
- inbound / outbound 聚类数；
- 每个聚类覆盖的接口、命中流量数、累计 DIFF 明细条数和代表 Flow；
- 上一轮已修复项、验证结果和剩余项。

命中流量数用于衡量影响面；累计 DIFF 明细条数可能被数组元素数量放大，不能直接当成独立问题数。
任务快照变化时重建受影响清单，不把不同 `update_time` 的数字直接比较。

### 2. 按影响范围生成本轮 worklist

当前轮的调查顺序按以下因素从高到低排列：

1. 覆盖流量数和影响接口数；
2. 是否改变错误码、响应主体、关键业务字段或调用链；
3. 是否可能是多个下游 DIFF 的共同上游原因；
4. 是否命中证据充分、可立即执行的确定性动作；
5. 修复后预计可消除的聚类和流量范围。

这是修复轮次的资源分配，不改变 `task-analysis.md` 的完整归因合同。聚类很多时，先深挖本轮
高影响 worklist，其余项保留在剩余清单；不要为了形式上的全覆盖而给每个聚类生成泛化建议。

### 3. 先过确定性动作门禁

在进入开放式代码分析前，逐个检查下列确定性模式。只有证据满足对应门槛时才能给出动作：

| 模式 | 最小证据 | 确定性动作 |
| --- | --- | --- |
| 动态字段或已知噪音 | 多 Flow 分布与字段语义证明其不承载业务结果 | 按 `diff-denoise.md` 确认后，使用 `noise-template-rule.md` 或 `remediation-noise.md` 预览精确 path 规则 |
| 时间精度或固定偏移 | 两侧表示同一业务时间，差值模式稳定，且精度不影响业务语义 | 使用 `remediation-noise.md` 的 `set-time-offset` 预览 |
| 无业务顺序的数组 | 长度和元素集合一致，稳定业务键唯一，重排后完整元素一致 | 使用 `remediation-noise.md` 的数组匹配预览；顺序有业务语义时禁止 |
| outbound instrumentation order-only | 同一 Flow 内 ES/业务 outbound 事件与对应 `*_before` 快照一对一存在，`mockResult` 均有效、命中同一 recorded pair，完整内容一致且仅相对位置反转 | 精确成对事件顺序匹配；不能扩大为全局 outbound 无序匹配，也不修改业务代码 |
| outbound 匹配异常 | 任务形态应有 Mock，且请求差异、调用次数、调用顺序或未命中证据明确；已先排除 instrumentation order-only | 按 `diag-mock.md` 修正精确匹配条件、调用顺序或录制缺口 |
| 已存在精确规则 | 当前父配置、mode、method、direction 和 path 已回读 | 更新精确规则；禁止新建重复规则或扩大到全局忽略 |

确定性门禁的结果只能是：

- `可执行`：证据、目标、动作和验证方法均明确；
- `不适用`：有证据排除该模式；
- `待进一步诊断`：缺少一项具体证据，不能生成修复结论。

噪音模板不得用于掩盖金额、状态、权限、库存、配置、业务对象 ID 或其他真实业务差异。

### 4. 对未命中项做代码下钻

只有高影响聚类未命中确定性动作时，才按 `diff-analysis.md` 和
`flow-diff-root-cause.md` 进入代码、日志、Trace、配置和部署分析。优先寻找能够解释多个聚类的
首个业务分叉点，而不是从最终响应逐字段打补丁。

重点检查：

- 录制与回放环境分支是否走了不同业务路径；
- local cache、全局变量、`sync.Once` 或启动期配置是否无法在回放环境复现；
- token、session、鉴权、签名或加解密是否依赖请求外状态；
- idgen、UUID、随机数和时间是否重新生成；
- 循环中的重复 outbound 或相同方法调用是否缺少稳定匹配维度；先区分业务调用顺序和 FTF `before`/result 观测事件顺序；
- 请求外异步状态、协程 context、singleflight 或组件边界是否导致漏录或错配。

进入目标仓库后先识别：

- 项目语言、模块边界、任务 PSM 对应的真实代码仓库和任务时点 commit；
- 是否已有 FTF SDK、回放请求判断、方法级代理或公共 helper；
- 是否为 BOS 壳应用：重点检查 `atum.yaml`、`dependency/business.go`、
  `dependency/capability.go` 和 `go.mod.properties`；
- 产生差异的逻辑位于壳应用还是二方包，是否需要两个仓库联动验证。

常见代码修复模式：

| 根因 | 修复方向 |
| --- | --- |
| 环境分支 | 仅对真实测试环境保留特殊分支，让 FTF 回放沿录制时业务路径执行；使用目标仓库已有的回放请求判断 |
| local cache | 对关键读取方法做方法级录制/回放，或让录制与回放两侧执行相同的缓存未命中路径 |
| token / session / 鉴权 / 加解密 | 包裹最小的解析或加解密方法，录制真实结果并在回放时读取，禁止绕过普通流量安全逻辑 |
| 启动期配置 | 代理请求实际读取的配置 getter，不假设回放实例拥有相同的 `init` / `sync.Once` 内存状态 |
| idgen / UUID / 随机数 / 时间 | 录制并回放生成结果；多次调用加入稳定业务参数或索引，避免按执行时序误配 |
| 重复 outbound | 比较录制与回放调用次数和顺序，修复首个请求参数或控制流分叉；不能只扩大 Mock 匹配范围 |

代码修复遵循目标仓库自身规范，并保持最小影响：

- 不改变普通真实流量的业务语义；
- 录制和回放成对设计，回放读取已录结果，录制记录真实结果；
- 多次调用使用稳定业务参数、索引或顺序维度，不能依赖随机值匹配；
- 优先复用目标服务已有 FTF helper 或方法级代理，不复制一套新的基础设施；
- 修改后运行目标仓库要求的编译、单测和静态检查。

BOS 壳应用优先在真正产生差异的二方包修复，再更新壳应用依赖并做联合验证。分别记录二方包和
壳应用的分支、commit、验证结果与交付关系；不得只改壳应用依赖而遗漏根因代码，也不得在未验证
二方包版本时声称壳应用已修复。

### 5. 落地并验证本轮动作

每个动作都必须绑定具体聚类、代表 Flow、证据和预期消除范围。

- 平台配置：先预览，获得用户要求的确认后执行，再按 owning Reference 回读精确 path 和配置。
- 业务代码：在目标仓库当前集成基线上创建修复分支，提交最小改动并完成本地验证。
- 部署和回放：属于独立写操作；只有用户已请求且对应流程允许时执行。使用相同筛选口径重新回放，
  再重新建立下一轮基线。

验证必须比较修复前后：

- 有 DIFF 的接口数和流量数；
- inbound / outbound 聚类数；
- 本轮目标聚类的命中流量数；
- 是否出现新聚类、回放失败或副作用。

配置保存、代码提交或任务创建成功都不等于 DIFF 已减少；只有回读和回放结果能证明本轮收敛。

### 6. 生成下一轮检查点

每轮保留一个可恢复的修复账本：

```text
轮次与任务快照
本轮基线
确定性动作判定
已落地变更
回读与回放结果
DIFF 净变化
剩余聚类优先级
下一轮单点任务
```

未解决项不得只写“建议继续分析”。每个待进一步诊断项必须缩小为：

- 一个聚类和一条代表 Flow；
- 已检查证据和已排除假设；
- 当前缺失的唯一关键证据；
- 下一位 Agent 或用户可直接执行的一项动作。

## Write Constraints

- 未经用户明确授权，不执行平台配置、代码提交、部署、录制或回放写操作。
- dry-run 与 execute 必须保持相同任务、PSM、聚类和修复参数。
- 写入结果未知时停止后续写入，先按 owning Reference 回读，不盲目重试。
- 一轮可以只完成部分高影响项，但不能把未分析聚类写成已修复或已归因。
- 只有证据证明是噪音时才创建噪音规则；业务问题必须修业务代码或配置。

## Results

- **本轮完成**：至少一项确定性修复已落地，完成回读，并通过新回放量化 DIFF 净变化。
- **部分完成**：修复已落地但部署或回放受阻；报告实际完成步骤、阻塞点和恢复动作，不宣称 DIFF
  已减少。
- **待进一步诊断**：本轮没有足够证据形成确定性修复；输出单聚类、单 Flow 的下钻任务，不输出
  大而全的可能性列表。
- **整体收敛**：当前范围内业务 DIFF 已修复，已证明噪音已按精确规则处理，剩余项均有明确的外部
  阻塞或验收结论。不要仅以聚类数为零判断业务正确性。
